# Enhanced Experience architecture

Use this map to locate the relevant components before changing code. Confirm current behavior in the linked source, then update the affected rows when entry points, responsibilities, or dependencies change.

## Package and entry points

| Area | Files | Entry points and scope |
| --- | --- | --- |
| Loading | [filelist.xml](filelist.xml), [ModConfig.xml](ModConfig.xml) | LuaCsForBarotrauma loads C# scripts from `CSharp/Shared` on both the server and the client. The package declares Barotrauma **1.13.5.0**, matching the locally installed executable checked on **2026-11-21**. |
| Orders and autonomous objectives | [ExpeditionPlugin.cs](CSharp/Shared/ExpeditionPlugin.cs) | `ExpeditionPlugin.Initialize` installs Harmony patches. `ReplaceOrderObjective` substitutes selected native objectives after `AIObjectiveManager.CreateObjective`. `InstallCrewObjectives` runs after `CreateAutonomousObjectives` and for existing crew on plugin load. The first authoritative AI update retries installation for bots whose controllers were not attached during objective creation. `DismissExpeditionOrders` runs after `SetOrder`. `Dispose` clears tracking state and unpatches. |

## Crew systems

| System | Main files and classes | Behavior, connections, and change points |
| --- | --- | --- |
| Expedition equipment | [AIObjectivePrepareForExpedition.cs](CSharp/Shared/AIObjectivePrepareForExpedition.cs), [ExpeditionPolicy.cs](CSharp/Shared/ExpeditionPolicy.cs) | Replaces `prepareforexpedition` with a persistent objective that checks suits, tools, oxygen, and medical supplies. Start at `InspectKit`, `Act`, and `FinishAttempt` for deficits, acquisition, and gear transfers. `ExpeditionPolicy` owns depth and flooding thresholds and item ranking. `ExpeditionPlugin.TrySetPlannedDepth` sets the optional plan on the active order. Acquired gear is recorded for return. |
| Exterior navigation, combat, and gathering | [ExteriorFollow.cs](CSharp/Shared/ExteriorFollow.cs) (`ExteriorFollow`, `Escort`, `Activity`) | Extends native `follow` in open water. `BeforeAI` manages escort state, `BeforeGoTo` and `LimitFollowDistance` coordinate movement, and `EscortCombatPriority` and `EscortSafetyPriority` arbitrate native combat and safety objectives. `AfterPick` and `AfterFixBody` track player gathering. The escort reacts to that activity, reserves its own resource target, and leaves gathered items in the bot's inventory for return. |
| Expedition return and inventory | [ExpeditionReturn.cs](CSharp/Shared/ExpeditionReturn.cs) (`ExpeditionInventory`, `ExpeditionReturn`) | Preparation and exterior follow start per-bot tracking. `RecordPickup` and the `Inventory.PutItem` hook track gear origins and loot. With a native return target and tracked expedition, `ExpeditionReturn.Act` delegates travel to the base objective and handles unloading on arrival. Start at `MoveItem`, `FindLocker`, and `SortNext` for storage and sorting. Issuing `return` dismisses prior preparation and follow orders. |
| Medical cleanup and cabinet sorting | [MedicalCleanupObjective.cs](CSharp/Shared/MedicalCleanupObjective.cs) (`MedicalCleanupObjective`, `MedicalCleanupItem`), [MedicalCabinetOrganizer.cs](CSharp/Shared/MedicalCabinetOrganizer.cs) | Doctor `cleanupitems` routes medical and poison items to their respective cabinets. See `Classify`, `FindCabinet`, and `ObjectiveConstructor` for classification, destination, and child objectives. `MedicalCabinetOrganizer.Organize` handles cabinet layout for both cleanup and expedition return. |
| Crew deconstruction | [CrewDeconstructionObjective.cs](CSharp/Shared/CrewDeconstructionObjective.cs) | Replaces the explicit bot order `deconstructitems` for all jobs. Native subobjectives still process manual marks. The added path finds unmarked onboard ores and plants with usable recipes, reserves an item and a machine, and uses native navigation and deconstruction. When eligible work is exhausted, it uses native order dismissal. |
| Autonomous repairs | [CrewRepairPriorities.cs](CSharp/Shared/CrewRepairPriorities.cs) (`CrewRepairPriorities`, `AutoFixLeaks`, `AutoRepairSystems`, `InspectEquipment`) | Coordinates autonomous leak and device work per occupied submarine. `Refresh` filters available crew and native-valid targets, reserves targets of active native repair orders, and assigns one task per worker using urgency, skill, job, distance, and commitment. Native subobjectives handle travel and repair. Failed targets have a brief per-worker retry delay. Idle engineers and mechanics visit safe equipment rooms via native GoTo. The same plan assigns each room to one bot and records visited rooms for 90 seconds. Explicit orders retain their native objectives. |
| Portable consumable maintenance | [MaintenancePatrol.cs](CSharp/Shared/MaintenancePatrol.cs) | Adds idle Assistant service for oxygen tanks and portable battery cells. Patrol checks the repair and defense plans before reserving work, releases untouched jobs on interruption, and keeps in-flight transfers for recovery. `IsPortableResource` excludes stationary power devices, fuel, and ammunition. `FindService` and `NeedsService` select work, while `Update`, `Act`, `Load`, and `Return` manage interruption and transfer. The plugin preserves patrol state when autonomous objectives are rebuilt. |
| Ship defense | [SecurityDefense.cs](CSharp/Shared/SecurityDefense.cs) (`SecurityDefense`, `DefensePlan`, `WeaponOperation`, `IntruderDefense`) | Assigns Security Officers to turrets or intruders using a shared plan per submarine. `Assign`, `ScoreTarget`, and `CanEngage` control assignments and target eligibility. The repair planner excludes assigned defenders so they do not reserve a repair simultaneously. Native turret operation uses the selected target, `CheckAutomaticLaunch` gates automatic fire, and the `Structure.AddDamage` hooks track hull attacks for targeting. |

## Cross-system checks

| When changing | Check these interactions |
| --- | --- |
| Priority or interruption | Routine repair, turret defense, and maintenance yield to active orders. Confirmed boarders and severe exterior leaks into occupied rooms may take priority over ordinary orders. Forced orders, steering, reactor operation, expedition-related orders, and native emergency safety retain precedence. The objective manager resumes the still-valid order after the emergency objective loses priority. Exterior follow explicitly puts urgent safety ahead of escort combat and interrupts gathering for threats or unsafe conditions. Check deselection, cancellation, and resumption together. |
| Movement or combat hooks | `AIObjectiveGoTo` supplies native routing for follow, equipment acquisition, return storage, and deconstruction. Keep follow patches scoped to the escort context. Both exterior follow and ship defense patch `HumanAIController.SpotEnemies`. Check both predicates when changing either. |
| Inventory and shared resources | Expedition gear and loot rely on inventory ownership transitions. Check return bookkeeping when changing pickups or transfers. Preserve access and capacity checks, item reservations, and cabinet sorting shared by cleanup and return. |
| Authority or compatibility | Shared behavior runs on the authoritative simulation through client guards. Harmony patches and internal-access bindings depend on the installed Barotrauma and LuaCs assemblies. |

[Run-All.ps1](Tests/Run-All.ps1) is the verification entry point. It validates XML, package configuration, and resources, then invokes [Verify-Expedition.ps1](Tests/Verify-Expedition.ps1) for client/server compilation and [ExpeditionChecks.cs](Tests/ExpeditionChecks.cs). It checks Lua syntax when `luac` is available. [README.md](README.md) indexes the single-player quickstart scenarios and recorded results under [Tests](Tests).

[Run-Quickstart.lua](Tests/Run-Quickstart.lua) is the LuaCs console entry point for the gameplay scenarios including the critical flooding and order resumption scenario (`coordination`). It accepts submarine `1` for every scenario and retains the scenario-specific submarine choices. It validates the active round, captures the selected scenario's existing assertions, and writes a separate status log. Each scenario requires a fresh round because its fixture changes game state and LuaCs reloads its execution context during the transition.
